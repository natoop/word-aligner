# 翻译词对齐服务能力评估报告

- 评估日期：2026-10-21
- 评估对象：`http://localhost:8000/api/v1/align`
- 运行形态：Docker 容器 `word-aligner-api-1`，镜像 `word-aligner:latest`，单 uvicorn worker
- 模型配置：XLM-R（`xlmr`），embedding layer 8，`matching_methods=mai`，主输出方法 `itermax`，`ALIGNER_DEVICE=cuda`
- 评估方式：黑盒 HTTP API，不修改服务代码与模型权重
- 结论适用范围：本次被测镜像、配置与硬件环境

---

## 1. 执行摘要

**总体结论：原始模型（raw）的通用词对齐质量达到可用水平；当前 `repair`（conservative / span-aware）在通用与换序数据上是净负收益，并且会生成缺少词级链接的 `refined` 组；长句性能受无条件 `mwmf` 计算拖累。生产环境应默认使用 raw `itermax`，在修复换序破坏与链接契约之前不要开启 repair。**

关键发现：

1. **通用质量可用但召回率优先瓶颈**：XL-WA 10 个欧洲语言对、2,413 句，raw `itermax` 平均 F1 **0.833**（平均 P 0.894 / R 0.781），单语言对 F1 范围 0.750–0.918。
2. **中英原子链接命中高，但组级精确度明显下降**：自建 63 句 / 184 个金标对，raw 原子链接命中 **91.8%**，组精确 **67.9%**，内容 token 全覆盖 **76.6%**；术语类最弱（组精确 25.0%，全覆盖 43.8%）。
3. **保守修正净负收益**：XL-WA 平均 F1 从 0.833 降至 0.769（**-6.4 点**），召回率下降 **11.0 点**，组过合并率从 2.7% 升至 8.5%；中英组精确从 67.9% 降至 50.5%，原子链接命中从 91.8% 降至 66.3%。`span-aware` 在本次全部样本上与 `conservative` 输出完全相同。
4. **换序场景被修正式精炼破坏**：raw 在换序类达到 83.3% 组精确，conservative 降至 40.5%；部分句子从 5/5 正确变为 1/5，且错误是"组平移"而非简单漏对齐。
5. **确定性规则精确率 100%，但覆盖面窄**：52 条 rule 链接全部命中金标，protected token 14/14 正确，规则零误配；但日期仅覆盖年/月，数量仅覆盖百分比，ISO 日期、日后缀、普通数字/单位/货币均未覆盖。
6. **规则识别到数值冲突时不会压制错误模型链接**：负控 `Feb 2025 → 2025年3月` 与 `15% → 20%` 中，模型分别产生 `Feb→3`、`%→20%` 的错误链接，相似度 0.90/0.94、置信度 0.41/0.54；规则因 key 不匹配而不生成链接，但也没有清除冲突的模型链接。
7. **置信度可用于排序，不可直接当概率阈值**：raw confidence AUROC 0.817–0.945，但 ECE 0.276–0.360，平均绝对校准误差约 32 个百分点。
8. **长句性能存在硬悬崖**：100 个短句对中位 1.24s；500 词单句 30.3s；520 词以上直接 HTTP 500。500×500 剖析中 `mwmf` 占 29.7s，是总耗时的绝对主因；4 并发相对串行仅 1.09x 加速。

### 上线建议（按优先级）

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| P0 | 生产默认 `method=itermax`、不传 `repair`；演示页默认改为"不修正" | raw 全面优于 conservative；演示页当前默认 conservative，会系统性低估服务质量 |
| P0 | 修复精炼器对非单调/换序区域的破坏，或将其限制在可证明单调的分句内 | 当前 `refined` 组会把正确关系平移成错误关系，属于静默语义错误 |
| P0 | 统一 `alignment_groups` 与 `links` 契约：`refined` 组必须带 `repaired` 链接，或明确标记为 group-only | 当前 `refined` 组 `links=()`，只读 `links` 的下游会丢失对齐证据 |
| P0 | `mwmf` 按需计算；对超长输入做子词级预检并返回 4xx | 长句 30s 延迟、520 词 500、单请求即可占满 CPU |
| P1 | 扩展日期与数量规则：ISO/斜杠日期、`日`后缀、数字/小数/千分位/单位/货币 | 当前规则覆盖面与用户对"日期/数量规范化"的预期不符 |
| P1 | 规则识别到同类 key 冲突时，删除或降权冲突模型链接 | 负控已证明模型会在数值实体上产生高相似度错误链接 |
| P1 | 置信度按语言/域重新校准，规则链接单独标注 | ECE 约 0.32，不能直接作为业务阈值；规则 1.0 会扭曲整体校准 |
| P2 | 增加 worker 或批处理能力，移除全局推理锁的吞吐瓶颈 | 4 并发仅 1.09x，GPU 在长请求中基本空闲 |
| P2 | 建立 XL-WA + 自建种子集的 CI 回归门槛 | 防止修复逻辑或模型升级造成静默回退 |

## 3. 评估方法与数据

### 3.1 服务能力边界

- 元数据声明支持 48 种语言、任意语言对；本次实测覆盖 10 个欧洲语言对与 EN-ZH，未覆盖 AR/KO/SV 等数据受限语言。
- 请求限制：1–100 个句对，单侧最多 10,000 字符；`method` 支持 `itermax` / `inter` / `mwmf`；`repair.strategy` 支持 `conservative` / `span-aware`。
- 不传 `repair` 时返回纯模型结果；传入后启用漏词修正与 Span 精炼。
- 本次所有性能数字来自同一宿主（RTX 2080 Ti，CUDA 可用）与单容器环境。

### 3.2 数据

**XL-WA（公开基准）**

- 仓库内数据版本：commit `f5c9ea26daa4e53e5f3fa133a45e1bede1db816d`，test split。
- 覆盖 10 个 EN-* 语言对：it/es/nl/ru/sl/bg/da/et/hu/pt，共 **2,413 句**。
- 许可证：CC BY-NC-SA 4.0；数据仅用于本次评估，不随代码分发（已加入 `.gitignore`）。
- EN-ZH、AR、KO、SV 等语言对受上游访问限制，未纳入公开基线。

**自建 EN-ZH 能力种子集**

- 63 个手工构造句对、184 个金标对，定义见 `eval/data/zh_en/capability_seed.jsonl`。
- 类别分布：

| 类别 | 句数 | 金标对 | 覆盖内容 |
| --- | ---: | ---: | --- |
| general | 10 | 44 | 普通陈述句、动宾/介宾结构 |
| term | 8 | 16 | 机构名、产品名、复合术语 |
| date | 10 | 22 | 月名、年份、ISO 日期、斜杠日期、日期换序 |
| quantity | 10 | 22 | 百分比、小数、千分位、单位、货币 |
| placeholder | 10 | 22 | `[[X]]`、`${name}`、`{{name}}`、HTML 标签、重复占位符 |
| reorder | 10 | 42 | 时间从句、定语从句、状语换序 |
| edge | 5 | 16 | 空结果、单 token、emoji、大小写、标点 |
| **合计** | **63** | **184** | |

- 金标用"源/目标子串"定义，评估时投影到服务返回的 token：先选完全包含于字符 span 的 token，若无则取字符重叠最大的 token，避免 jieba 切分差异造成的标注偏差。
- 负控：`date-10`（Feb 不应映射 3月）、`qty-10`（15% 不应映射 20%）、`ph-10`（`[[A]]` 不应映射 `[[B]]`）、`reorder-10`（禁止整句组）。
- 种子集为本次评估自建，规模有限且无第二标注者一致性数据；结论应视为能力探测，而非语言对总体估计。

### 3.3 指标

| 指标 | 定义 |
| --- | --- |
| 组精确（group_exact） | 返回的某个 `alignment_groups` 与金标投影后的源/目标 token 集合完全相等 |
| 组包含（group_contained） | 金标集合被某个返回组完整包含（允许组更大） |
| 原子链接命中（link_hit） | 至少一条 `links` 原子链接连接金标源/目标集合 |
| 证据命中（evidence_hit） | 原子链接或相交 group 提供证据（覆盖 group-only 的 refined 组） |
| 内容 token 全覆盖（full_coverage） | 金标两侧所有内容 token 均被证据覆盖；标点不计入分母 |
| 规则精确率 | `origin=rule` 的链接中命中金标对的比例 |
| 过合并率 | 组级预测中，一个组覆盖多个金标连通分量的比例（XL-WA 评测器） |
| 置信度 AUROC / ECE / Brier | 以链接是否正确为标签的排序能力、期望校准误差、Brier 分数 |
| 链接 P/R/F1 | XL-WA 官方 token-level 链接指标，bootstrap 200 次给出 95% CI |

- 组精确与全覆盖是主指标；原子链接指标单独报告，用于识别"组正确但 links 为空"的契约问题。
- `full_coverage` 可能被错误的大组满足，因此必须结合组精确、负控和规则精确率解读。

### 4.3 方法对比（IT，raw）

| 方法 | P | R | F1 | 置信度 AUROC | 说明 |
| --- | ---: | ---: | ---: | ---: | --- |
| itermax | 0.899 | 0.741 | **0.813** | 0.871 | 综合最佳，默认选择合理 |
| inter | **0.949** | 0.702 | 0.807 | 0.762 | 最保守，适合高精度场景 |

- `inter` 的置信度排序能力明显弱于 itermax/mwmf；若下游依赖 confidence 过滤，itermax 更合适。
- `mwmf` 的 AUROC 最高，但代价是长句下不可接受的 CPU 开销（见第 7 节）。

| edge | 16 | 62.5% | 93.8% | 81.3% | 56.3% | 75.0% | 93.8% |
| **总体** | **184** | **67.9%** | **91.8%** | **76.6%** | **50.5%** | **66.3%** | **70.1%** |

补充总体指标：

| 指标 | raw | conservative | 变化 |
| --- | ---: | ---: | ---: |
| 组包含率 | 67.9% | 60.3% | -7.6 |
| 证据命中率（含 group-only） | 91.8% | 81.0% | -10.8 |
| 平均 token 覆盖率 | 86.0% | 76.9% | -9.1 |
| 全部金标精确的句子 | 22/63 | 17/63 | -5 |
| 全部金标有原子链接的句子 | 52/63 | 33/63 | -19 |
| 全部内容 token 全覆盖的句子 | 31/63 | 34/63 | +3 |

配对转移（184 个金标对，raw → conservative）：

- 组精确：正确→错误 **34**，错误→正确 **2**。
- 原子链接：正确→错误 **47**，错误→正确 **0**。
- 全覆盖：正确→错误 **20**，错误→正确 **8**。

conservative 在少数句子上改善了全覆盖（如 `term-04` 的短语扩展、`date-04`、`qty-08`、`edge-04`），但整体以破坏为主；原子链接层面没有任何一对从错误变为正确。

### 5.2 规则与受保护 token

| 规则域 | 命中金标对 | 规则精确率 | 结论 |
| --- | ---: | ---: | --- |
| 日期 | 16/22 | 100% | 只处理月名、四位年份、`数字+年/月`；ISO/斜杠日期、`日`后缀未覆盖 |
| 数量 | 2/22 | 100% | 只处理百分比；小数、千分位、单位、货币未覆盖 |
| 占位符 | 14/22 | 100% | `[[X]]`、`${name}`、`{{name}}`、HTML 标签；重复占位符按出现顺序正确配对 |
| 术语 | 1/22 | 100% | 仅有极少数与日期/数量规则重合的数值型术语 |

- 52 条 rule 链接全部命中金标，**规则误配为 0**；protected 对 14/14 精确，重复 `[[X]]` 没有串位。
- 规则的弱点不是"错"，而是"窄"：例如 `2026-03-31` 整体是一个 token，不被任何日期规则识别；`Feb 2025 → 2025年3月` 中只有 `2025` 被规则命中，`Feb` 仍由模型错误映射到 `3`。
- 规则命中后，相关模型链接会被移除并替换为 rule 链接；但规则只返回"匹配成功"的 span，**当同类 key 不匹配时不会返回冲突 span，也就不会清除模型错误链接**（见 `app/temporal_rules.py`、`app/quantity_rules.py` 的实现）。

### 5.3 负控结果

| 用例 | 禁止关系 | 实际结果 | 来源 | similarity | confidence |
| --- | --- | --- | --- | ---: | ---: |
| date-10 | Feb → 3月 | `Feb → 3` 出现 | model | 0.9046 | 0.4118 |
| qty-10 | 15% → 20% | `% → 20%` 出现 | model | 0.9415 | 0.5431 |
| ph-10 | `[[A]]` → `[[B]]` | 未出现 | — | — | — |
| reorder-10 | 整句组 | 未出现 | — | — | — |

- 规则来源的禁止链接：**0**；任意来源的禁止链接：**2**，均为模型高相似度错误。
- 这两条错误说明模型会把"数值/实体一致性"当作语义相似度问题：`Feb` 与 `3月` 在同一句法槽位、`%` 与 `20%` 都是百分比符号，embedding 相似度很高。
- `ph-10` 的 protected 机制成功阻止了跨占位符误配；整句组负控也通过。

### 5.4 术语与短语

- `term-01`：`World → 世界卫生组织` 只形成部分覆盖，`guidelines → 指南` 正确；组精确 1/2。
- `term-04`：raw 将 `Amazon → 亚马逊`、`Web → 云`、`cloud → 云`、`services → 服务` 分散对齐，两个复合术语都没有形成完整组；conservative 通过扩展把 `Services provides cloud computing → 科技 提供 云 计算` 合成一组，虽然覆盖了金标 token，但组边界和语义角色错误。
- 结论：当前模型/精炼器缺少术语词典或短语级约束，长术语的对齐应视为"部分可用"，不能直接用于术语抽取或翻译记忆构建。

## 6. 修正与精炼分析

### 6.1 为什么 conservative 会破坏正确结果

`app/span_refinement.py:1128` 的 `_partition_region` 在分句区域内做**单调区间划分**：源端区间和目标端区间的起点同时向前推进，隐含假设两侧顺序一致。对于目标语发生状语前置、时间从句换序、定语从句后置等非单调结构，这个假设不成立；优化器只能把源端区间与位置相近但语义不同的目标区间配对，产生"组平移"。

精炼组由 `_make_refined_span`（`app/span_refinement.py:1308`）构造，该函数明确返回：

```python
links=(),
```

因此 `refined` 组只存在于 `alignment_groups`，不在 `links` 中；但 `unaligned_*` 又把组内 token 视为已对齐。这造成三个后果：

1. 只消费 `links` 的下游会丢失这些对齐；
2. 组级 evidence 看似覆盖率提高，原子链接指标却大幅下降；
3. 错误组无法通过 `links` 的相似度/置信度做二次过滤。

### 6.2 典型破坏案例

| 用例 | raw 结果 | conservative 结果 | 结论 |
| --- | --- | --- | --- |
| reorder-02 `The system sends a notification before the backup starts.` / `系统在备份开始前发送通知。` | 5/5 金标对完整正确 | 1/5；`notification → 开始`、`starts → 通知`、`system sends → 在` | 时间从句换序被单调划分破坏 |
| reorder-05 `The document that the manager signed was archived.` / `经理签署的文件已归档。` | 4/4 完整正确 | 1/4；`manager → 文件`、`document that → 签署` | 定语从句换序被破坏 |
| reorder-01 `The callback fires after the node is cloned.` / `节点被克隆后回调触发。` | 3/5 完整正确（callback/after/cloned） | 0/5；`callback fires → 被`、`after → 克隆`、`node is → 回调` | 正确关系被整体平移 |
| gen-04 `Please restart the service after changing the configuration.` / `修改配置后请重启服务。` | restart/service 正确，2/4 覆盖 | 0/4；`restart the → 配置`、`service → 后`、`after → 请` | 普通状语前置也触发破坏 |
| gen-05 `The sensor detects temperature changes in real time.` / `传感器实时检测温度变化。` | 4/5 全覆盖；sensor/detects/temperature/changes 正确 | 1/5；`detects → 实时`、`temperature changes → 检测`、`real time → 变化` | 状语换序导致整段语义错位 |

`span-aware` 在上述所有用例上与 conservative 输出完全一致；其增量扩展逻辑（`app/span_refinement.py:287` 之后）在本次样本中没有产生任何差异。

### 6.3 少数改善场景

- `term-04`：conservative 把 `Services provides cloud computing` 扩成一组，使两个术语金标对达到 full coverage；但组边界错误，组精确仍为 0。
- `date-04`、`qty-08`、`edge-04`：conservative 使这些句子达到"全部内容 token 全覆盖"。
- 这些收益不足以抵消 34 个组精确正确→错误、47 个原子链接正确→错误的损失。

### 6.4 契约与文档不一致

- `README.zh-CN.md:141` 声称时间从句换序会生成 `origin: "refined"` 组，"并在组内和句子级 `links` 中提供 `origin: "repaired"` 的明确词级链接"。
- 实测：63 句中 conservative 仅产生 **1 条 `repaired` 链接**，而 `refined` 组有 **100 个**；绝大多数精炼组没有任何词级链接。文档描述与响应契约不一致。
- 演示页 `app/static/align.html:101` 将 conservative 设为默认选项，因此用户默认看到的是质量更差、契约更不完整的配置。

## 7. 鲁棒性与性能

### 7.1 输入校验与 Unicode

| 检查 | 结果 |
| --- | --- |
| 空 source / 空 target / 纯空白 | 全部 422，错误定位到字段 |
| 非法语言代码 | 422 |
| 10,001 字符 | 422 |
| 空句对列表 / 101 个句对 | 422 |
| 字符偏移与 token 文本 | 全部一致 |
| emoji、组合字符、箭头 `5→3` / `6→4` | 安全；箭头作为 protected token 产生 rule 链接 |
| 重复占位符 `[[X]]` | 按出现顺序正确配对 |

### 7.2 长句悬崖

| 输入 | 结果 |
| --- | --- |
| 500 词 | 200，30.3s |
| 510 词 | 200，32.0s |
| 520 / 550 / 600 词 | HTTP 500，`alignment_failed` |
| 400 词（补充探测） | 约 16.5s |
| 混合批中 1 个超长句 | 整个请求 500，无部分结果；重试短句正常 |

- 请求层允许 10,000 字符，但 XLM-R 的最大子词长度是 512。英文约 520 词即触顶；`app/alignment.py:132` 捕获到子词超限后抛出 `ValueError`，最终被包装成 500 `alignment_failed`，而不是 4xx 输入错误。
- 错误信息只有 `Failed to align sentence pair at index N`，不包含"超长/子词数/上限"等可操作信息。

### 7.3 耗时根因

容器内对 500×500 对齐做分段计时（单次请求）：

| 阶段 | 耗时 |
| --- | ---: |
| `mwmf`（networkx `max_weight_matching`） | **29.716s** |
| XLM-R embedding（CPU 计时段） | 0.816s |
| word embedding 平均 | 0.012s |
| 相似度矩阵 | 0.008s |
| 相对相似度 | 0.002s |
| fwd/rev | 0.001s |
| itermax | 0.010s |
| softmax | 0.002s |
| **总计** | **约 30.3s** |

- 服务配置 `ALIGNER_MATCHING_METHODS=mai`，`app/alignment.py:156` 会无条件计算 `mwmf`，即使请求的 `method=itermax`；`mwmf` 是 CPU/networkx 实现，GPU 在长请求中基本空闲（观测 GPU 0%，容器 CPU 100%）。
- 因此长句延迟近似随 token 数平方增长（补充探测：100/200/300/400/500 重复词请求约 1.26/3.00/7.53/16.32/31.02s），且与用户选择的方法无关。

### 7.4 并发

- 4 个并发请求，每个 25 句对：串行中位 1.230s，并发中位 1.126s，**1.09x**。
- 服务为单 uvicorn worker，且 `app/alignment.py:256` 的 `_inference_lock` 将模型推理串行化；并发请求主要在排队，无法利用 GPU 或多核。
- 对交互式演示，短句延迟可接受（100 对 1.24s）；对批处理或高并发 API，当前吞吐不足。

## 8. 失败分类与生产风险

| 编号 | 失败模式 | 触发条件 | 影响 | 证据 |
| --- | --- | --- | --- | --- |
| F1 | 精炼器单调假设破坏换序 | repair 开启，目标语非单调 | 静默语义错误，组平移 | reorder-01/02/05, gen-04/05 |
| F2 | refined 组无 links | repair 开启 | 下游只读 links 时丢失对齐；组/链接契约不一致 | 100 组 vs 1 条 repaired 链接 |
| F3 | 术语/复合短语碎片化 | 长术语、产品名、机构名 | 术语抽取、TM 构建不可用 | term 组精确 25% |
| F4 | 规则覆盖窄 | ISO/斜杠日期、日后缀、普通数字/单位/货币 | 日期/数量类全覆盖仅 68%/77% | date-02、qty 规则 |
| F5 | 数值实体错误链接不被压制 | 源/目标同类 key 不匹配 | 高相似度错误难以用阈值过滤 | date-10、qty-10 |
| F6 | 长输入计算悬崖 | 约 520+ 英文词 / 512 子词 | 30s 延迟或 500，批处理雪崩 | 500/510/520 词 |
| F7 | 批次原子失败 | 批内任一句超长/异常 | 整批失败，无部分结果，错误信息弱 | 混合批 500 |
| F8 | 并发吞吐低 | 多请求并发 | 单请求占满 CPU，GPU 空闲 | 1.09x，单 worker + lock |
| F9 | 置信度不可直接解释 | 任何依赖概率阈值的下游 | 过度自信导致错误自动决策 | ECE 0.28–0.36 |

**生产风险排序**

1. **静默语义错误**（F1/F2）高于"未对齐"：错误组看起来完整，人工复核和下游都难以发现。
2. **长输入资源耗尽**（F6/F8）：一个 510 词请求占用 CPU 30s；并发数个即可拖垮服务。
3. **数值实体错误**（F5）：日期/数量/金额场景中，错误链接可能直接进入结构化数据。
4. **契约不一致**（F2）：不同下游读 `links` 或 `alignment_groups` 会得到不同覆盖，难以排查。
5. **置信度误用**（F9）：把 0.8 当成"80% 正确"会导致自动化门槛设置错误。

## 9. 建议与验收门槛

### 9.1 P0：上线前必须处理

1. **默认关闭 repair**
   - 生产请求显式 `method=itermax`，不传 `repair`。
   - 演示页 `app/static/align.html:101` 默认改为 `none`，或在页面标注"conservative 为实验特性"。
   - 在 README 中明确 raw 为推荐配置，repair 为实验配置。

2. **修复精炼器的非单调区域**
   - 在 `_partition_region` 前检测区域是否单调；非单调区域跳过保守精炼，或复用已有的时间换序专用路径并扩展其覆盖。
   - 对 `refined` 组要求至少一条内部链接，否则不要输出该组（避免"组存在但无证据"）。
   - 增加 reorder-01/02/05、gen-04/05 的回归用例，断言组精确不下降。

3. **统一 links / groups 契约**
   - 方案 A：为每个 `refined` 组生成内部 `repaired` 链接（文档承诺的行为）。
   - 方案 B：在 schema 中显式增加 `group_only: true` 或 `evidence: "group"`，并更新所有消费者。
   - 无论哪种方案，`unaligned_*` 的语义必须与 `links`/`groups` 一致。

4. **长输入保护**
   - 在推理前按模型 tokenizer 计算子词数，超过 512 返回 422/413，错误信息包含"子词上限 512，请拆分句子"。
   - 将 `mwmf` 改为按需计算：仅当 `method=mwmf` 或 repair 需要回退时才计算；`itermax` 请求不应触发 networkx。
   - 对 100–200 词以上的输入增加超时/队列策略，避免单请求长时间占用 worker。

### 9.2 P1：质量与可解释性

5. **扩展日期规则**
   - 支持 `YYYY-MM-DD`、`YYYY/MM/DD`、`DD/MM/YYYY`（需语言/地区消歧）、`Month DD, YYYY`、`DD Month YYYY`。
   - 支持中文 `YYYY年M月D日` 的整体 key，并允许源/目标 token 边界不同。
   - 对识别到日期类型但 key 不匹配的源 span，删除冲突模型链接或显著降权。

6. **扩展数量规则**
   - 普通数字/小数/千分位/单位/货币/百分比统一 key；区分 `1,000` 与 `1000`。
   - 对金额、百分比、计量单位分别建模，避免"数值相同但单位不同"被误配。
   - 同样在 key 冲突时压制模型链接。

7. **术语与短语**
   - 增加可选术语表（源/目标短语对）作为受保护规则，命中后生成 rule 链接。
   - 对长度超过 `max_source_span`/`max_target_span` 的术语，优先保持整体组，不要拆成局部组。

8. **置信度校准**
   - 按语言对/领域收集校准集，使用 isotonic/Platt 校准；输出 `calibrated_confidence` 或置信度分档。
   - 规则链接的 1.0 单独标注为 `rule`，避免与模型置信度混用。
   - 在文档中明确：confidence 适合排序，不是正确概率。

### 9.3 P2：吞吐与运维

9. **并发与批处理**
   - 评估多 worker + 每 worker 独立模型，或 GPU 批处理；移除全局锁或按模型实例分锁。
   - 增加请求队列、超时和背压；对大批量请求返回逐句状态而非整批 500。

10. **监控与回归**
    - 记录每请求的 token 数、子词数、方法、repair 策略、耗时、规则命中数、refined 组数、links 数。
    - 对 `mwmf` 耗时、超长请求、500 率、refined 组无链接比例设告警。

### 9.4 CI 基线门槛（建议）

| 门槛 | 建议阈值 |
| --- | --- |
| XL-WA 10 对 raw F1 | 不低于本次基线 1 个百分点（按语言对分别设阈值） |
| 中英种子集 raw 组精确 | ≥ 65%（当前 67.9%） |
| 中英种子集 raw 全覆盖 | ≥ 75%（当前 76.6%） |
| 开启 repair 后的组精确 | 不得低于 raw - 2 点；否则阻断发布 |
| 规则精确率 | 100%；规则来源禁止链接必须为 0 |
| protected 对命中率 | 100% |
| 负控任意来源禁止链接 | 0（当前 2，需修复模型链接压制） |
| 520 词输入 | 返回 4xx 且信息可操作，不得 500 |
| 500 词 p95 延迟 | 目标 < 5s（当前 30s，需先解决 mwmf） |
| 4 并发加速比 | 目标 > 2x（当前 1.09x） |

## 10. 结论与适用边界

**适合的场景**

- 以 raw `itermax` 做词级/短语级候选对齐，供人工复核、术语候选挖掘、翻译记忆辅助。
- 短句、受控领域、可接受部分漏对齐的场景。
- 对受保护 token（模板变量、HTML 标签、箭头）有强一致要求的场景。

**不适合的场景**

- 直接开启 repair 做生产对齐；当前会把正确的换序关系改错。
- 依赖 `links` 做自动化下游消费，而 repair 产生大量 group-only 对齐。
- 长文档/整段输入；520 词即失败，500 词需 30s。
- 对置信度做硬阈值自动决策；概率未校准。
- 日期、金额、数量等数值实体的高精度抽取；规则覆盖窄且模型会产出高相似度错误链接。

**最终建议**

> 将当前版本定位为"raw 词对齐引擎"而非"自动修复引擎"。先以 raw `itermax` 上线并设置输入长度保护；把 repair 作为实验特性隔离。优先修复非单调精炼与 links/groups 契约，再谈规则扩展和置信度校准。
